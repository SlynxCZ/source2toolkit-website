---
title: Hooking
---

Source2Toolkit hooks with **KHook** — Metamod:Source's own detour library, on
the one engine Metamod runs for the whole server. If you have written a
Metamod 2.0 plugin, you already know the API. The SDK wraps it in a set of
`KHOOK_*` macros so a hook is one line in your class, and the toolkit does the
resolving, attaching and tearing down for you.

---

# One engine for everyone

The toolkit does **not** run a hook engine of its own. It takes KHook from
Metamod when it loads and hands that same engine to every plugin through
`TOOLKIT_KHOOK_INTERFACE`.

This is deliberate. `CallOriginal` and `Supersede` walk the handler chain of
the engine that owns the patch. Two independent engines patching the same
address cannot see through each other — one of them silently calls the other's
trampoline instead of the real original. One engine means one chain per
address, so the core's hooks, your plugin's hooks and the hooks of the Metamod
plugins next to you compose correctly.

You never fetch it. `TOOLKIT_EXPOSE` declares the globals and
`TOOLKIT_SAVEVARS` fills them:

```cpp
Plugin g_Plugin;
TOOLKIT_EXPOSE(my_plugin, g_Plugin);

bool Plugin::Load(PluginId id, IToolkitAPI* api, char* error, size_t maxlen, bool late)
{
    TOOLKIT_SAVEVARS();   // KHook is live from here on
    ...
}
```

# A hook is one line

Every hook is a member of your class, declared with a macro from
`IToolkitHooks.h` (pulled in by `IToolkitPlugin.h`). The macro takes the
hook's type from the **handler** it names — the handler's first parameter is
the hooked class, the rest are the function's own arguments — so nothing is
spelled twice and MSVC needs no CTAD. Declare the handler above the macro.
The context is the enclosing object, so the handlers are ordinary members.

```cpp
class Plugin final : public IToolkitPlugin
{
public:
    bool Load(PluginId id, IToolkitAPI* api, char* error, size_t maxlen, bool late) override;
    bool Unload(char* error, size_t maxlen) override;

    KHook::Return<void> Hook_GameFrame(ISource2Server* pThis, bool simulating, bool bFirstTick, bool bLastTick);
    KHook::Return<bool> Hook_FireEvent(IGameEventManager2* pThis, IGameEvent* event, bool bDontBroadcast);
    KHook::Return<void> Hook_PostThink(CCSPlayerPawn* pThis, double flFrameTime, float flUnknown);

private:
    KHOOK_VIRTUAL(m_hGameFrame, &ISource2Server::GameFrame, &g_pSource2Server, nullptr, &Plugin::Hook_GameFrame);   // Post only
    KHOOK_VIRTUAL(m_hFireEvent, &IGameEventManager2::FireEvent, KHOOK_VTABLE("server", "CGameEventManager"),
                  &Plugin::Hook_FireEvent, nullptr);                                                             // Pre only
    KHOOK_MEMBER(m_hPostThink, "CCSPlayerPawn::PostThink", &Plugin::Hook_PostThink, nullptr);
};
```

The last two arguments are always the Pre and the Post callback. Pass both if
you need both sides; `nullptr` leaves a side empty.

`KHOOK_INIT()` in `Load()` resolves and installs every hook the plugin
declared this way, `KHOOK_DESTRUCT()` in `Unload()` takes them all down:

```cpp
bool Plugin::Load(PluginId id, IToolkitAPI* api, char* error, size_t maxlen, bool late)
{
    TOOLKIT_SAVEVARS();

    g_pSource2Server = api->GetSource2Server();   // anything a hook reads has to be set first

    if (!KHOOK_INIT())
        TOOLKIT_LOG(this, "Some hooks were not installed, see above.\n");

    return true;
}

bool Plugin::Unload(char* error, size_t maxlen)
{
    KHOOK_DESTRUCT();
    return true;
}
```

A hook whose target cannot be resolved — a gamedata entry that is missing, a
vtable not found — is logged and skipped; the rest still go in, and
`KHOOK_INIT()` returns `false` so you know.

<Callout type="info">
  Order matters: `KHOOK_INIT()` reads the instance pointers and calls the
  toolkit, so it goes after `TOOLKIT_SAVEVARS()` and after you have set the
  globals your virtual hooks name.
</Callout>

# Virtual hooks

`KHOOK_VIRTUAL(member, function, target, pre, post)`. The **function** says
where in the vtable the hook goes:

- `&Class::Method` — the index is read out of the member function pointer,
  nothing written down by hand;
- an integer — a hardcoded index;
- a gamedata offset name (`"CCSPlayerController::Respawn"`) — read from
  gamedata at `KHOOK_INIT()`.

The **target** says what it attaches to:

- `&pInstance` — a pointer to the instance pointer (`&g_pSource2Server`).
  It is read at `KHOOK_INIT()`, not when the hook is constructed, so the
  global may still be null at that point;
- `KHOOK_VTABLE(module, class)` — a whole vtable by RTTI name, covering every
  object that shares it. The module is a name (`"server"`, `"engine2"`) or a
  pointer to an `IToolkitModule*` you fill in at load (`&modules::server`);
- `nullptr` — you attach it yourself: `m_hX.Init(pInstance)` or
  `m_hX.InitGlobal(vtable)`.

```cpp
KHOOK_VIRTUAL(m_hClientCommand, &ISource2GameClients::ClientCommand, &g_pSource2GameClients, &Plugin::Hook_ClientCommand, nullptr);
KHOOK_VIRTUAL(m_hSendNetMessage, &CServerSideClientBase::SendNetMessage, KHOOK_VTABLE("engine2", "CServerSideClient"), &Plugin::Hook_SendNetMessage, nullptr);
KHOOK_VIRTUAL(m_hRespawn, "CCSPlayerController::Respawn", KHOOK_VTABLE("server", "CCSPlayerController"), &Plugin::Hook_Respawn, nullptr);
```

A vtable hook hooks the class, not one instance — every client goes through
`m_hSendNetMessage`, and `pThis` tells you which one.

<Callout type="warn">
  A gamedata offset that is missing reads as `-1`, and a hook configured at
  `-1` lands one slot **before** the vtable — on the typeinfo pointer, which
  corrupts every later by-name vtable lookup on that class. The wrapper refuses
  a negative index and logs the key instead of installing the hook.
</Callout>

# Function hooks

Anything a signature scan can find is hookable — no vtable, no interface.
`KHOOK_MEMBER` is for a function with a `this` (the handler's first parameter),
`KHOOK_FUNCTION` for a free function (the handler takes only the function's own
arguments). The **target** is where the address comes from:

- a gamedata entry name — resolved through `IToolkitGameConfig::ResolveSignature`,
  which reads the entry's library and finds it by exported symbol or by
  pattern, whichever the entry uses;
- an `IToolkitMemory` address you already have;
- a capture-less lambda returning the address, called at `KHOOK_INIT()` — for
  what the toolkit already resolved, so nothing is scanned twice;
- `nullptr` — you place it yourself with `m_hX.Init(address)`.

```cpp
// bool INetworkMessageProcessingPreFilter::FilterMessage(const CNetMessage*, INetChannel*)
KHook::Return<bool> Hook_FilterMessage(INetworkMessageProcessingPreFilterCustom* pThis, const CNetMessage* pData, INetChannel* pChannel);
KHook::Return<int64_t> Hook_TakeDamageOld(CBaseEntity* pThis, CTakeDamageInfo* pInfo, CTakeDamageResult* pResult);

KHOOK_MEMBER(m_hFilterMessage, "INetworkMessageProcessingPreFilter::FilterMessage", &Plugin::Hook_FilterMessage, nullptr);
KHOOK_MEMBER(m_hTakeDamageOld, [] { return ADDR_TAKE_DAMAGE_OLD(); }, &Plugin::Hook_TakeDamageOld, nullptr);
```

<Callout type="info">
  Function hooks are the answer when a class has a **non-primary** vtable —
  a secondary vtable is a separate table elsewhere in `.rodata`, and a
  by-name lookup only ever finds the primary one. That is exactly why the
  toolkit hooks `FilterMessage` by signature rather than by vtable.
</Callout>

# Inside a handler

The object that was actually called arrives as the first parameter; the rest
are the function's own arguments:

```cpp
KHook::Return<void> Plugin::Hook_FireOutputInternal(CEntityIOOutput* pThis, CEntityInstance* pActivator, CEntityInstance* pCaller,
                                                    void* variantValue, float delay, void* unk01, void* unk02)
{
    const char* outputName = pThis->m_pDesc->m_pName;
    ...
    return { KHook::Action::Ignore };
}
```

A handler returns `KHook::Return<T>`: the action, plus the value when the
hooked function returns one:

```cpp
return { KHook::Action::Supersede };          // void handlers
return { KHook::Action::Override, false };    // handlers with a return type
```

| `KHook::Action` | meaning |
|---|---|
| `Ignore` | the handler did nothing |
| `Override` | the original still runs, but your return value is used (Pre only) |
| `Supersede` | the original is skipped entirely, your return value is used (Pre only) |

The toolkit's own listeners — `REG_CON_LISTENER`, `HOOK_GAME_EVENT`, net
message hooks, entity output listeners — return `Action`, which is the same
type: `IToolkitTypes.h` aliases it to `KHook::Action`.

<Callout type="warn">
  `Supersede` skips the original **for every remaining Pre handler too**. If
  you called the original yourself and only want to stop KHook calling it a
  second time, supersede is still the right answer — but hooks registered
  after yours will not see it run.
</Callout>

# Calling the original

From a Pre handler, `CallOriginal` runs the real function with the arguments
you give it — then supersede, so KHook does not run it a second time. The
member declared by the macro forwards `->` to the KHook object underneath, so
everything KHook offers is a `->` away:

```cpp
sv_autobunnyhopping.Set(true);
m_hCheckJumpButtonLegacy->CallOriginal(pThis, mv);
sv_autobunnyhopping.Set(false);

return { KHook::Action::Supersede };
```

In a Post handler the original has already run; its result is a call away:

```cpp
unsigned long id = KHook::GetOriginalReturn<unsigned long>();
```

# Removing hooks

`KHOOK_DESTRUCT()` detaches every hook and deletes it — deleting is what takes
the detour down. One hook can also go on its own: `m_hX.Destruct()`.

<Callout type="warn">
  Take every hook down before your plugin unloads. A live hook pointing into an
  unmapped library crashes the server on the next call.
</Callout>

# Under the hood

The macros wrap plain KHook objects — `KHook::Virtual`, `KHook::Member`,
`KHook::Function` — in `CToolkitVirtualHook`, `CToolkitMemberHook` and
`CToolkitFunctionHook`. Each wrapper owns its KHook object, registers itself in
a per-plugin list that `KHOOK_INIT()` / `KHOOK_DESTRUCT()` walk, and remembers
its target until the toolkit is ready to resolve it.

You can still hold a raw KHook object where the wrapper does not fit.
`KHOOK_NEW` (`IToolkitTypes.h`) writes its mem-initializer without repeating
the type:

```cpp
KHook::Virtual<ISource2Server, void, bool, bool, bool>* m_hGameFrame = nullptr;

Plugin::Plugin() :
    KHOOK_NEW(m_hGameFrame, &ISource2Server::GameFrame, this, nullptr, &Plugin::Hook_GameFrame)
{
}

// Load(): attach; Unload(): Remove, then delete
m_hGameFrame->Add(g_pSource2Server);
```

A raw hook is yours to attach (`Add`, `AddGlobal` on a vtable stand-in,
`Configure(addr)`), detach and delete.

# Coming from SourceHook

Earlier Source2Toolkit builds ran a private SourceHook engine. The mapping is:

| SourceHook | KHook |
|---|---|
| `SH_DECL_HOOK*` + `SH_ADD_HOOK` | `KHOOK_VIRTUAL(..., &pInstance, ...)` |
| `SH_ADD_DVPHOOK` / `SH_ADD_MANUALDVPHOOK` | `KHOOK_VIRTUAL(..., KHOOK_VTABLE(module, class), ...)`, with a gamedata offset name or an index as the function |
| `SH_DECL_INLINEHOOK*` + `SH_ADD_INLINEHOOK` | `KHOOK_MEMBER` / `KHOOK_FUNCTION` with a gamedata name, an address or a lambda |
| `META_IFACEPTR` / `SH_IFACEPTR` | the first handler parameter |
| `RETURN_META` / `RETURN_META_VALUE` | `return { action }` / `return { action, value }` |
| `MRES_IGNORED` / `MRES_HANDLED` | `KHook::Action::Ignore` |
| `MRES_OVERRIDE` | `KHook::Action::Override` |
| `MRES_SUPERCEDE` | `KHook::Action::Supersede` |
| `SH_CALL(...)` | `m_hX->CallOriginal(pThis, ...)` |
| `SH_RESULT_ORIG_RET(T)` | `KHook::GetOriginalReturn<T>()` |
| `SH_REMOVE_HOOK_ID` | `KHOOK_DESTRUCT()` / `m_hX.Destruct()` |

<Callout type="warn">
  `KHook::Action` and `META_RES` are **not** numerically compatible — `META_RES`
  has an extra `MRES_HANDLED` at 1, which shifts everything after it. There is
  nothing left to cast between: the toolkit's `Action` *is* `KHook::Action`.
</Callout>
